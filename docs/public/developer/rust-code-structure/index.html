Rust code structure audit

Current responsibility map for Tauri commands and the incremental extraction path.

Implementation reference Evolving Informative

This audit compares the current Rust source with the target boundaries in Backend structure. The source tree partially matches the intended dependency direction, but the Tauri command boundary is not yet consistently thin.

Current responsibility map

Area Current state Assessment
lib.rs Registers commands and initializes application resources Appropriate composition root
application/computation.rs Owns typed resolved-chart calculation orchestration Matches the application layer
application/transit.rs Owns typed transit validation and series orchestration Matches the application layer
astronomy.rs Defines the provider trait and selects Rust astronomy adapters Useful boundary; provider construction can later be injected
astrology.rs Backend-neutral body selection and model-driven aspect rules over resolved positions; no Tauri, YAML, or engine dependency Domain logic (~900 lines, the second-largest file); the clearest domain/ extraction candidate, not yet in that boundary

Main finding

commands/workspace.rs is currently about 2,800 lines. Size alone is not the problem: it contains unrelated reasons to change. Provider routing and fallback policy change the same module as Nominatim HTTP behavior, native folder-picker processes, workspace YAML writes, chart serialization, response normalization, and Tauri DTOs.

The calculation commands do delegate Rust calculation to typed application services. They still own backend selection, Python HTTP payloads, fallback behavior, and response normalization. The application boundary is therefore incomplete rather than absent.

A second gap sits above the command layer: astrology.rs, houses.rs, and event_time.rs already have no Tauri, YAML, or engine dependency and match the domain responsibility Backend structure describes, but no domain/ module exists yet to hold them. backend.rs, ephemeris_manager.rs, jpl_backend.rs, and swisseph.rs are similarly domain-adjacent or infrastructure-shaped code living at the crate root rather than under infrastructure/. The target shape below carries a domain/ boundary forward from Backend structure so both documents describe the same end state.

Target command shape

Commands should deserialize transport inputs, call one application use case, and serialize its result:

commands/
├── workspace.rs       # thin workspace invoke adapters
├── charts.rs          # thin chart CRUD/import adapters
├── calculation.rs     # chart and cross-aspect invoke adapters
├── transits.rs        # transit persistence and compute adapters
├── location.rs        # location/timezone invoke adapters
├── dialogs.rs         # desktop dialog invoke adapter
├── ephemeris.rs
└── legacy_storage.rs

application/
├── workspace.rs       # workspace and chart use cases
├── computation.rs     # resolved chart calculation
├── compute_router.rs  # Rust/Python selection, fallback, provenance
├── transit.rs
└── location.rs        # location resolution port/use case

domain/                # carried forward from Backend structure's target
├── chart.rs           # today: astrology.rs (body selection, aspect rules)
├── model.rs
├── calculation.rs
├── relation.rs
├── workspace.rs
├── event_time.rs      # today: event_time.rs, permissive parser to replace
└── error.rs

infrastructure/
├── workspace_yaml/    # filesystem repository and serialization
├── geocoding/         # Nominatim client and timezone lookup
├── dialogs/           # platform process/plugin implementation
├── python_sidecar/    # today: backend.rs (sidecar lifecycle, HTTP client)
├── astronomy/         # today: astronomy.rs, jpl_backend.rs, swisseph.rs, houses.rs
└── ephemeris/         # today: ephemeris_manager.rs (BSP catalog/cache)

This mirrors the four-layer split in Backend structure rather than introducing a second target shape; domain/ and infrastructure/ here are the same boundaries that doc names, applied to the files that currently exist at the crate root.

Splitting the command file without moving its logic would improve navigation but not responsibility boundaries. Extract complete use cases: application orchestration first, external mechanisms behind infrastructure ports second, then leave only Tauri adapters in commands/.

Recommended extraction order

  1. Move native folder selection into infrastructure/dialogs.
  2. Move Nominatim and timezone implementation into infrastructure/geocoding behind a location service.
  3. Move workspace, chart, and transit YAML writes into a repository beside the existing loader.
  4. Move Rust/Python route selection, fallback, and response normalization into application/compute_router.rs.
  5. Split the remaining thin command adapters by use case.
  6. Move astrology.rs and houses.rs into domain/; move backend.rs into infrastructure/python_sidecar/; move ephemeris_manager.rs into infrastructure/ephemeris/; move astronomy.rs, jpl_backend.rs, and swisseph.rs into infrastructure/astronomy/.
  7. Replace event_time.rs’s permissive parser with a canonical validated time type in domain/event_time.rs.
  8. Move unit tests with the extracted logic and retain command-level integration tests for serialization and Tauri-visible behavior.

This order preserves command names and frontend contracts throughout the migration.

Testing boundary

  • Domain/application tests should call pure services without constructing Tauri state.
  • Infrastructure tests should exercise YAML, HTTP adapters, process selection, and provider behavior explicitly.
  • Command tests should focus on DTO conversion, error mapping, and registered behavior.
  • Cross-language routing and normalization remain integration/parity tests.

Track those layers in the Testing strategy.
